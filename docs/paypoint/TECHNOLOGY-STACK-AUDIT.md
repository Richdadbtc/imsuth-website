# IMSUTH PayPoint technology stack audit

**Audit date:** 11 October 2026  
**Scope:** `backend/` only; the public IMSUTH website and production infrastructure were excluded  
**Result:** Compliant with the mandated architecture, subject to the verification limitations below

## Executive summary

IMSUTH PayPoint is a server-rendered Django application. Its authored frontend consists of HTML5 Django templates, CSS3 and a small vanilla JavaScript ES6 module. The backend is Python/Django with Django REST Framework and Celery. PostgreSQL, Redis, Gunicorn, NGINX and Docker Compose are represented in the application and deployment configuration.

No React, Vue, Angular, Next.js, TypeScript, jQuery, Bootstrap JavaScript, Node.js backend, package-manager manifest or frontend build pipeline was found. No framework migration or dependency removal was necessary. No public website or production infrastructure file was modified by this audit.

The current application has no custom modal component; destructive/confirmation affordances use the native browser confirmation API through the shared vanilla JavaScript module.

The OpenAPI schema is generated by `drf-spectacular`; the configured Swagger documentation renderer is a documentation utility, not an authored application framework or project build dependency. It does not own PayPoint workflow or financial state.

## UI integration status

All application templates are connected through one of the following server-side mechanisms:

- Dashboard and domain pages use named Django class-based views.
- Patient and invoice creation use Django forms with server-side cleaning and model/service validation.
- Payment initiation uses a Django form and backend `Payment.create_intent`; the browser cannot mark an electronic payment as confirmed.
- Authentication and password recovery use Django authentication views and templates.
- Revenue, finance, reconciliation and audit screens query permission-scoped backend views.
- Receipt display and print formatting are generated from backend receipt/payment/invoice records.
- The REST API is routed through DRF viewsets and a protected test-webhook API view.
- The shared base and pagination templates are structural includes rather than standalone routes.
- The 403 template is used by Django permission handling rather than a direct business route.

Seven POST-form templates include Django CSRF tokens. GET forms provide search/date/status filtering and do not mutate state.

### Source-of-truth controls

- Approved tariffs and invoice totals are resolved on the Python backend.
- Payment confirmation validates provider/test-adapter evidence server-side.
- Database constraints and transactional locking protect idempotency and receipt uniqueness.
- Financial approvals enforce maker-checker rules on the backend.
- Reconciliation and revenue reporting use persisted confirmed-payment records.
- Role permission checks protect both Django views and DRF endpoints.
- Authentication, CSRF handling and audit logging remain server-side.
